응답 유실 재현 확인

테스트용 가짜 PG 가 "거래는 성공으로 저장하고 응답만 잃는" 상황을 의도대로 만드는지 확인한 기록이다.

2026-11-22 · 브랜치 feat/volume10-incident (main 7380737 기준, 미커밋) · W10 1단계

결론

부품 수준에서 의도대로 재현된다. 실제 PgClient 는 timeout 으로 실패했고, 가짜 PG 에는 그 주문의 SUCCESS 거래가 하나 남았으며, 같은 주문으로 조회하면 SUCCESS 가 나온다. 결제 생성 요청은 한 번뿐이다.

주문 API 부터 시작해 "그래서 Payment 가 PENDING 으로 남는다"까지는 아직 확인하지 않았다. 3단계 사고 실험에서 확인한다.

무엇을 만들려 했나

우리 서버(PgClient) ── 결제 요청 ──▶ 가짜 PG
                                     ├ 거래를 SUCCESS 로 저장
                                     └ 응답을 붙잡고 보내지 않음 (1.5s)
우리 서버: 읽기 제한 시간 초과 → 실패
결과: PG 에는 성공 거래, 우리 서버는 결과를 모름

3단계에서 복구할 대상이 이 상태다. PG 에 실제 거래가 남아야 "같은 거래를 조회해서 마무리"할 수 있다.

어떻게 확인했나

테스트: apps/commerce-api/src/test/kotlin/com/loopers/incident/LocalPgFixtureTest.kt 의 storesSuccessThenDropsResponse (85~99번 줄). 프로덕션 PgClient 를 그대로 만들어 가짜 PG 주소로 호출한다.

단언이 아무 경우에나 통과하지 않는지

가짜 PG 가 응답을 붙잡지 않고 바로 연결을 끊게 바꿔서 같은 테스트를 돌렸다 (응답 붙잡기 800ms → 0). timeout 이 아닌 실패라서 테스트가 깨져야 한다.

두 경우 예외 이름은 같고 근본 원인만 다르다. timeout 을 가려내는 건 92번 줄의 원인 단언이다. 확인 뒤 설정을 원래대로 되돌렸고 5개 테스트가 다시 통과했다.

테스트를 고친 곳

처음에는 91번 줄을 ResourceAccessException 으로 적었다. 실행해 보니 실제로는 RestClientException 이 와서 실패했다. 코드가 아니라 테스트에 적은 예상이 틀렸던 것이라 이름만 실제에 맞췄다. 92번 줄(원인이 timeout)과 95~97번 줄은 바꾸지 않았다. W5 PgClientTest.failsOnReadTimeout 도 읽기 timeout 을 같은 방식으로 단언한다.

아직 확인하지 않은 것

  • 3단계 주문 API → 확정 API → 응답 유실 → Payment PENDING 유지 → 재고 예약 유지. 지금은 PgClient 한 부품만 돌렸다.
  • 범위 상대가 진짜 pg-simulator 가 아니라 같은 계약을 따르는 테스트용 서버다. pg-simulator 는 접수 후 결과를 비동기 콜백으로 정하지만, 가짜 PG 는 응답 유실 대상을 접수 즉시 SUCCESS 로 저장한다.
  • 범위 응답 헤더를 보내기 전에 붙잡는 경우만 확인했다. 헤더는 보내고 본문 중간에 끊기는 경우는 만들지 않았다.

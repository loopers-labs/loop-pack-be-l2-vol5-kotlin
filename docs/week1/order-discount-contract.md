- 이번 주 범위: 문서와 관찰 테스트만. `apps/commerce-api/src/main`은 안 건드립니다.
- 작성자 / 작성일: 홍예슬 / 2026-09-11

## 0. 기준 문장

> "구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 한다."

원래 티켓에는 "주문에 쿠폰을 적용할 수 있어야 해요" 한 줄만 있었습니다.
제품 담당자와 범위를 확인하고 위 문장으로 고쳤습니다.

- 이 문장으로 정해진 것: 누가(구매자), 언제(확정 전), 확정 후 금액 보존
- 아직 안 정해진 것: 확정이 언제인지, 구매자 말고 누가 할 수 있는지, 남의 주문에 요청하면 뭐라고 답할지. 아래 질문 목록으로 넘깁니다

## 1. 요구 분류

한 문장을 세 갈래로 나눕니다. 섞으면 개발자의 추측이 제품 정책이 됩니다.

### 1-1. 확인된 사실 (2개)

기준 문장에 그대로 적혀 있습니다.

- **F-1** 구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있습니다.
- **F-2** 확정된 할인 금액은 이후에도 유지됩니다.

### 1-2. 실습 장면의 조건 (4개)

이번 장면에서만 참입니다. 인터페이스나 데이터 구조에 미리 못 박지 않습니다.

| # | 조건 | 일반화하면 안 되는 이유 |
| --- | --- | --- |
| C-1 | 한 주문에 쿠폰 한 장 | 실제 제품은 쿠폰 여러 장이나 운영자 강제 할인을 가질 수 있습니다. 그래서 요청에 쿠폰 배열이나 우선순위를 미리 넣지 않고, 한 장을 영구한 사실로 굳히지도 않습니다 |
| C-2 | 최종 금액 = 원금 - 할인액 | 배송비나 세금, 부분 환불이 끼면 원금이 무엇인지부터 달라집니다. 한 줄 식으로 끝나지 않습니다 |
| C-3 | 같은 요청은 저장된 결과를 재사용 | 이번 장면은 쿠폰이 한 장이라 주문과 쿠폰 조합이 곧 요청 식별자입니다. 쿠폰이 여러 장이 되면 무엇이 같은 요청인지부터 다시 정해야 합니다(Q-2) |
| C-4 | 만료는 요청 시작 시각으로 판단 | 이번 장면은 요청 하나가 동기로 끝나서 시작 시각이 하나로 정해집니다. 예약 주문이나 배치, 재시도가 끼면 요청 시작이 여러 개가 됩니다(Q-1) |

### 1-3. 제품 담당자에게 물을 질문

기준: 답이 갈릴 때 사용자 응답 / 저장 데이터 / 권한 중 하나가 달라지는 것만 남깁니다.

#### Q-1. 쿠폰 만료는 언제를 기준으로 판단하나?

(a) 사용자가 쿠폰을 고른 시각 · (b) 요청이 시작된 시각 · (c) 주문이 확정된 시각

- 달라지는 것: 사용자 응답. (a)면 할인가로 진행되고, (b)(c)면 만료 오류가 나갑니다.
- 지금은: (b). 요청 시작 시각으로 판단하라는 조건이 이미 주어져 있습니다(C-4).
- 틀렸을 때: 만료를 재는 곳 한 군데만 고치면 되고 저장 구조는 건드릴 일이 없습니다.

#### Q-2. 같은 쿠폰을 여러 장 가질 수 있나?

- 달라지는 것: 저장 데이터. 여러 장이면 `couponId` 만으로는 어느 장을 썼는지 알 수 없습니다.
- 지금은: 사용자당 한 장. `couponId`로 구분된다고 봅니다.
- 틀렸을 때: 되돌리기 비쌉니다. 같은 요청인지 어떻게 알아볼지(INV-005), 요청에 뭘 담을지, 보유 쿠폰을 어떻게 저장할지가 한꺼번에 바뀝니다.

#### Q-3. "주문 확정"은 언제를 말하나?

(a) 주문을 만든 시점 · (b) 결제가 끝난 시점 · (c) 생성과 별개인 확정 요청 시점

- 달라지는 것: 저장 데이터. 할인액을 고정해서 저장하는 시점이 달라집니다.
- 지금은: (c). 기준 문장이 "확정 전에 적용할 수 있고"라고 했으니 생성과 확정 사이에 구간이 있습니다.
- 틀렸을 때: 쿠폰을 언제까지 붙일 수 있는지, 금액이 언제부터 안 바뀌는지가 둘 다 흔들립니다. 금액을 고정하는 자리도 옮겨집니다.

확정이 언제인지 모르면 금액이 언제부터 안 바뀌는지도 말할 수 없습니다.
그래서 혼자 정해버리는 대신 질문으로 남겼습니다.

#### Q-4. 운영자나 CS도 남의 주문에 쿠폰을 적용할 수 있나?

- 달라지는 것: 권한. 행위자가 늘면 소유권 검사와 감사 기록 대상이 달라집니다.
- 지금은: 구매자 본인만. 기준 문장의 "구매자는"에 근거합니다.
- 틀렸을 때: 되돌리기 비쌉니다. 주문 주인만 바꿀 수 있다는 규칙과 사용자 식별 헤더의 뜻, 감사 기록이 한꺼번에 바뀝니다.

#### Q-5. 남의 주문에 요청하면 "권한 없음"인가 "주문 없음"인가?

- 달라지는 것: 사용자 응답. 존재를 숨기면 주문 ID를 잘못 넣은 경우와 구분이 안 됩니다.
- 지금은: 존재를 숨깁니다. 남의 주문을 건드렸을 때 그 주문이 있다는 것조차 드러내지 않기로 했습니다.
- 틀렸을 때: 오류를 어떤 상태 코드로 바꿀지 한 군데와 테스트만 고치면 됩니다. 대신 화면 문구가 바뀝니다.

없는 번호를 넣었을 때와 주소를 잘못 썼을 때가 똑같이 나온다는 걸 아래 관찰 표에서 확인했습니다.
이 질문도 결국 같은 문제입니다.

## 2. 현재 API 오류 계약 관찰

쿠폰 API는 아직 없습니다. 대신 이미 돌아가는 `/api/v1/examples`가 실패를 어떻게 표현하는지 봅니다.

```bash
./gradlew :apps:commerce-api:test --tests 'com.loopers.example.interfaces.api.ContractClassificationTest'
```

### 2-1. 관찰 표

`ContractClassificationTest` 실행 결과입니다. 테스트 5개, skip 0, 실패 0.

| 입력 | status | `meta.result` | `meta.errorCode` | `data` | 계약 의미 | 요청자의 다음 행동 |
| --- | --- | --- | --- | --- | --- | --- |
| 존재하는 숫자 ID | `200` | `SUCCESS` | `null` | 있음 | 정상 조회 | 응답 사용 |
| `abc` | `400` | `FAIL` | `Bad Request` | 없음 | 문법 오류 | 입력 수정 |
| 없는 숫자 ID (`-1`) | `404` | `FAIL` | `Not Found` | 없음 | 대상 자원 없음 | 재조회 · 대체 흐름 |
| 매핑 안 된 URL | `404` | `FAIL` | `Not Found` | 없음 | 요청 처리기 없음 | 경로 수정 |

### 2-2. 관찰에서 확인한 것

- 없는 번호를 넣었을 때와 주소를 잘못 썼을 때의 응답이 완전히 같습니다. 받는 쪽에서는 번호를 고쳐야 할지 주소를 고쳐야 할지 알 방법이 없습니다.
- 오류 코드를 HTTP 상태 이름에서 그대로 만들어 쓰고 있습니다. 그래서 오류 코드에 상태 코드 이상의 정보가 없습니다.
  실패 종류를 늘리려면 상태 코드와 분리된 식별자가 필요합니다.
- 쿠폰 실패 네 가지를 한 코드로 합치면 요청자가 다음에 뭘 할지 고를 수 없습니다.
  주문 목록으로 돌아갈지, 다른 쿠폰을 고를지, 쿠폰 적용 화면을 닫을지가 전부 같은 응답으로 나갑니다.

## 3. 반드시 지킬 규칙 · INV-001 ~ 006

W2에서 테스트 이름과 지표가 같은 번호를 씁니다. 번호의 뜻은 바꾸지 않습니다.

규칙은 클래스 이름이 아니라 언제나 참이어야 하는 상태로 씁니다. "Order 엔티티를 쓴다"는 규칙이 아닙니다.

반례는 규칙이 맞는지 확인하려고 붙이는 게 아닙니다. **규칙 문장을 고치려고 붙입니다.**

### INV-001 · 주문 소유권

쿠폰이 적용된 주문의 주인은 언제나 그 요청을 보낸 사람입니다.

- 출처: 구매자가 확정 전에 쿠폰을 적용할 수 있다는 제품 약속(F-1). 다만 운영자도 되는지는 아직 안 물어봤습니다(Q-4)
- 반례: 남의 주문에 `X-USER-ID`만 바꿔서 요청
- 기대: 주문이 안 바뀌고 거절됩니다. 그 주문이 있다는 걸 드러낼지 말지는 아직 안 정해졌습니다(Q-5)
- 책임 후보: 주문 객체

### INV-002 · 적용 가능 장수

확정 전 주문에는 쿠폰이 최대 한 장 붙습니다.

- 출처: 한 주문에 쿠폰 한 장이라는 실습 조건(C-1). "확정 전"이 언제까지인지는 아직 안 정해졌습니다(Q-3)
- 반례: 같은 주문에 다른 쿠폰 두 장을 연달아 적용
- 기대: 두 번째가 실패하고 붙어 있는 쿠폰은 1장 그대로입니다
- 책임 후보: 주문 객체

### INV-003 · 금액 경계

최종 금액은 원금에서 할인액을 뺀 값입니다. 할인액은 0원보다 작아질 수 없고 원금보다 커질 수도 없습니다.

- 출처: 최종 금액은 원금에서 할인액을 뺀 값이라는 실습 조건(C-2)
- 반례 ① 원금 10,000원에 100% 할인 쿠폰
- 반례 ② 원금 10,000원에 15,000원 정액 할인 쿠폰
- 기대: ① 할인액 10,000원, 최종 금액 0원으로 성공합니다. ② 최종 금액이 음수가 되지 않습니다 (원금까지만 깎을지 거절할지는 아직 안 정했습니다)
- 책임 후보: 할인 금액을 확정하는 곳

첫 번째 반례 때문에 문장을 고쳤습니다. "할인액은 원금보다 작습니다"라고 쓰면 전액 할인에서 깨지니까 "원금 이하"여야 합니다.

두 번째 반례로는 문장을 고칠 필요가 없었습니다. 대신 아직 안 정한 게 하나 있다는 걸 알았습니다.
규칙은 끝난 뒤의 상태만 정하지 거기까지 가는 방법은 정하지 않습니다.

### INV-004 · 확정 결과 보존

주문이 확정된 뒤에는 쿠폰 정책이나 상품 가격이 바뀌어도 할인액과 최종 금액이 그대로 남습니다.

- 출처: 확정된 할인 금액은 이후에도 유지된다는 제품 약속(F-2). 확정이 언제인지는 아직 안 정해졌습니다(Q-3)
- 반례: 10% 쿠폰으로 확정 → 정책을 20% 로 변경 → 같은 주문 다시 조회
- 기대: 저장된 할인액과 최종 금액이 확정 시점 값 그대로입니다
- 책임 후보: 확정할 때 값을 남기는 곳 (아래 D-2 결정과 이어집니다)

### INV-005 · 중복 요청

같은 주문에 같은 쿠폰을 여러 번 요청해도 할인액과 응답은 한 번 요청했을 때와 같습니다.

- 출처: 같은 요청은 저장된 결과를 재사용한다는 실습 조건(C-3)
- 반례: 같은 `orderId` + `couponId` 요청을 연달아 두 번
- 기대: 두 번째 응답이 첫 번째와 같고 할인이 두 번 쌓이지 않습니다
- 책임 후보: 적용 진입점 또는 저장소의 유니크 제약 (어디서 막을지는 아직 안 정했습니다)

"같은 쿠폰"이 무슨 뜻인지가 아직 애매합니다. 쿠폰 종류를 말하는지 발급받은 한 장을 말하는지는 물어봐야 압니다(Q-2).

### INV-006 · 만료 경계

적용에 성공한 쿠폰은 요청이 시작된 시각에 아직 유효했습니다.

- 출처: 만료는 요청 시작 시각으로 판단한다는 실습 조건(C-4). 어느 시각을 기준으로 볼지는 아직 안 정해졌습니다(Q-1)
- 반례: 자정에 끝나는 쿠폰을 `23:59:59.900`에 요청 시작. 처리 중에 자정을 넘김
- 기대: 요청 시작 기준이면 성공합니다. 처리 완료 기준이면 실패합니다
- 책임 후보: 요청 시작 시각을 한 번만 정해서 넘겨주는 곳

반례를 그냥 "만료된 쿠폰으로 요청"이라고 쓰면 아무것도 확인할 수 없습니다. 어느 기준으로 재든 똑같이 실패하니까요.
요청이 시작된 순간과 처리가 끝난 순간, 그 사이에 만료 시각이 걸쳐야 두 해석이 갈립니다.

### 제약 조건

이번 구현에서 선택할 수 있는 범위를 좁히는 조건입니다. 앞의 규칙과는 성격이 다릅니다.

- 외부 결제 시스템이 없습니다. 주문 확정과 결제를 이어붙이지 않습니다.
- 공통 템플릿 프로젝트 안에서 구현합니다. 응답 봉투와 예외 처리 구조를 새로 만들지 않고 그대로 씁니다.
- 이번 주는 제품 코드를 바꾸지 않습니다. 그래서 여기 적은 결정은 전부 W2에서 처음 코드로 옮겨집니다.

## 4. 외부 계약

요청자가 내부 구현을 몰라도 쓸 수 있어야 합니다.

| 항목 | 값 |
| --- | --- |
| method · path | `POST /api/v1/orders/{orderId}/discount` |
| 사용자 식별 | `X-USER-ID` 요청 헤더 |
| request | `couponId` |
| success | 주문 · 원금 · 할인 · 최종 금액 |
| 기본형과 다르게 갔다면 그 차이와 이유 | 차이 없음. 과제가 제시한 기본형을 그대로 씁니다 |

### 4-1. 실패마다의 의미

실패 목록은 UC-01에서 그대로 가져왔습니다.

> **Use case UC-01 · 주문에 쿠폰 적용**
> 주 사용자: 구매자
> 시작 조건: 구매자 소유 주문이며 아직 확정되지 않음
> 시작 사건: `couponId` 선택
> 성공 결과: 할인 결과 기록과 최종 주문 금액 반환
> 실패 결과: 주문 없음 / 소유자 다름 / 주문 확정 / 쿠폰 사용 불가
> 종료 조건: 성공한 할인 결과 기록은 이후 정책·가격 변화에도 동일

계약 의미와 HTTP, 오류 식별자, 요청자의 다음 행동은 제가 정했습니다.

| 실패 | 계약 의미 | HTTP | 오류 식별자 | 요청자의 다음 행동 |
| --- | --- | --- | --- | --- |
| 주문 없음 | 그런 주문이 없습니다 | 404 | `ORDER_NOT_FOUND` | 주문 목록으로 돌아갑니다 |
| 소유자 다름 | 위와 같게 응답합니다 | 404 | `ORDER_NOT_FOUND` | 주문 목록으로 돌아갑니다 |
| 주문 확정 | 주문이 더 이상 바뀌지 않는 상태입니다 | 409 | `ORDER_NOT_MODIFIABLE` | 쿠폰 적용 화면을 닫고 주문 상세로 갑니다 |
| 쿠폰 없음 | 보유 쿠폰 목록에 없습니다 | 404 | `COUPON_NOT_FOUND` | 쿠폰 목록을 다시 받아옵니다 |
| 쿠폰 사용 불가 | 목록에는 있지만 지금 쓸 수 없습니다 (만료·이미 사용) | 409 | `COUPON_NOT_USABLE` | 다른 쿠폰을 고릅니다 |
| 이미 쿠폰이 있음 | 이 주문에 쿠폰이 벌써 한 장 붙어 있습니다 | 409 | `COUPON_ALREADY_APPLIED` | 붙어 있는 쿠폰을 보여줍니다 |

**"쿠폰 사용 불가"를 둘로 나눈 이유.** 쿠폰이 목록에 아예 없는 것과, 목록에는 있는데 못 쓰는 것은
요청자가 할 일이 다릅니다. 앞쪽은 목록이 낡은 것이라 다시 받아와야 하고, 뒤쪽은 다른 쿠폰을 고르면 됩니다.

반대로 만료와 이미 사용은 합쳤습니다. 둘 다 "다른 쿠폰을 고른다"로 같습니다.
사용자에게 보여줄 문구는 다르겠지만 그건 응답 메시지로 처리합니다.

**"이미 쿠폰이 있음"은 UC-01 목록에 없습니다.** 그런데 한 주문에 쿠폰 한 장이라는 규칙(INV-002)을 지키려면
이 실패가 나가야 합니다. 규칙에서 나온 실패라 표에 넣었습니다.

**주문 없음과 소유자 다름의 식별자가 같습니다.** 남의 주문이라는 사실조차 숨기기로 했기 때문입니다(Q-5).
식별자를 다르게 하면 그 자체로 주문이 있다는 게 새어나갑니다.

대신 잃는 게 있습니다. 내 주문인데 번호를 잘못 친 사람과 남의 주문을 건드린 사람이 화면에서 똑같이 보입니다.
담당자가 "밝혀도 된다"고 답하면 소유자 다름만 403 `ORDER_FORBIDDEN`으로 떼어냅니다.

**원금보다 큰 할인은 이 표에 없습니다.** 원금까지만 깎을지 아예 거절할지를 아직 안 정했기 때문입니다(맨 아래 제안 처리 기록 A-3).
원금까지만 깎기로 하면 성공이라 표에 들어올 일이 없고, 거절하기로 하면 여기에 한 줄이 늡니다.

## 5. 내부 경계 결정 (3개)

### D-1 · 오류를 구분하는 방식

**검토한 선택지**

| | 선택지 | 장점 | 단점 |
| --- | --- | --- | --- |
| 1 | 지금 `ErrorType`에 업무 오류를 계속 추가 | 손댈 곳이 가장 적습니다. 기존 예외 처리 구조를 그대로 씁니다 | 업무 의미가 HTTP 상태에 묶입니다. 나중에 배치나 이벤트에서 같은 오류를 쓰기 어렵습니다 |
| 2 ✅ | 업무 오류 코드를 도메인에 두고 API 경계에서 HTTP로 변환 | 같은 404 안에서도 실패를 구분할 수 있습니다. 응답 봉투를 안 바꿔도 됩니다 | 업무 코드와 상태 코드를 잇는 변환을 관리해야 합니다. 빠뜨리면 응답이 흔들립니다 |
| 3 | 예외 타입 계층을 작게 만듭니다 | 복구 방식이 다른 실패를 타입으로 묶을 수 있습니다 | 규칙마다 클래스를 만들면 타입이 빠르게 늡니다. 외부에 내보낼 코드는 따로 필요합니다 |
| 4 | `sealed` 결과 타입으로 성공과 실패를 함께 반환 | 호출자가 실패 처리를 빠뜨릴 수 없습니다 | 예외를 던지는 지금 흐름과 이어줄 계층이 필요해 변경이 큽니다 |

**고른 것**: 2번. 업무 오류 코드를 도메인에 두고, API 경계에서 HTTP 상태로 바꿉니다. 도메인은 HTTP를 모릅니다.

**버린 대안과 이유**: 1번을 버렸습니다. 앞에서 테스트로 확인했듯이 지금은 오류 코드를 HTTP 상태 이름에서 그대로 만들어 씁니다.
그래서 같은 404 안에서 "주문이 없다"와 "쿠폰이 없다"를 구분할 방법이 없습니다.
1번은 손댈 곳이 제일 적지만 이 문제가 그대로 남습니다.
3번과 4번은 변경 범위가 이번 주제에 비해 큽니다.

**그래서 달라지는 것**: 응답 모양은 그대로 두고 오류 코드만 업무 이름으로 바뀝니다.
W2에서 변환표를 만들 때 빠진 항목을 잡는 테스트가 필요합니다.

### D-2 · 확정 값을 저장할지 매번 계산할지

**검토한 선택지**

| | 선택지 | 장점 | 단점 |
| --- | --- | --- | --- |
| 1 | 조회할 때마다 그 시점 정책으로 다시 계산 | 정책이 바뀌면 바로 반영됩니다. 저장할 값이 줄어듭니다 | 이미 끝난 주문 금액이 따라 바뀝니다 |
| 2 ✅ | 적용할 때 계산해서 저장하고 이후 다시 계산하지 않음 | 과거 주문 금액과 판단 근거가 안정적입니다 | 값을 남기는 책임이 생깁니다. 언제 남길지 정해야 합니다 |

**고른 것**: 2번. 쿠폰을 적용할 때 할인액과 최종 금액을 계산해서 저장하고, 이후 다시 계산하지 않습니다.

**버린 대안과 이유**: 1번을 버렸습니다. 확정 뒤에는 금액이 안 바뀌어야 한다는 규칙 때문입니다(INV-004).
매번 다시 계산하면 쿠폰 정책이 10%에서 20%로 바뀔 때 이미 끝난 주문 금액까지 따라 바뀝니다.
취향 문제가 아니라 규칙이 구조적으로 깨지는 것입니다.

**그래서 달라지는 것**: 확정할 때가 아니라 적용할 때 저장합니다.
같은 요청이 다시 오면 저장해둔 결과를 돌려줘야 하는데(C-3), 그러려면 적용하는 순간 이미 값이 남아 있어야 합니다.
다만 이 값이 언제부터 못 바뀌는지는 확정이 언제인지 답을 들어야 정해집니다(Q-3).

### D-3 · 호출 순서를 숨길 책임 경계

**검토한 선택지**

| | 선택지 | 장점 | 단점 |
| --- | --- | --- | --- |
| 1 | Facade가 조회·검증·계산·저장을 차례로 호출 | 흐름이 한눈에 보이고 따라가기 쉽습니다 | 규칙이 Facade에 흩어집니다. 다른 입구가 생기면 같은 순서를 또 써야 합니다 |
| 2 ✅ | 주문이 `applyDiscount` 하나로 순서를 감춤 | 쿠폰 장수와 금액 경계를 주문 안에서 지킵니다. 밖에서 알아야 할 게 적습니다 | 소유권과 만료는 밖에서 값을 받아야 합니다 |
| 3 | 주문과 쿠폰 사이에 도메인 서비스를 둡니다 | 두 객체를 조합하는 자리가 분명해집니다 | 주문의 규칙이 주문 밖으로 나갑니다. 주문만 봐서는 어떤 규칙이 지켜지는지 알 수 없습니다 |

**고른 것**: 2번. `order.applyDiscount(coupon, now)` 하나로 순서를 감춥니다. 쿠폰 장수와 금액 경계는 주문이 직접 지킵니다.

**버린 대안과 이유**: 1번을 버렸습니다. 흐름이 한눈에 보인다는 게 장점이지만 규칙이 Facade 여기저기 흩어집니다.
나중에 관리자 화면이나 배치처럼 다른 입구가 생기면 같은 순서를 또 써야 하는데,
한 군데만 빠뜨려도 쿠폰 장수나 금액 경계가 깨집니다.
3번은 주문의 규칙을 주문 밖으로 꺼내는 셈이라 같은 문제가 남습니다.

**그래서 달라지는 것**: 전부 감출 수는 없습니다. 주문 주인이 맞는지, 쿠폰이 아직 살아 있는지를 판단하려면
요청자가 누구이고 지금이 몇 시인지를 밖에서 받아야 합니다. 주문을 꺼내오고 저장하는 일도 밖에 남습니다.

| A-3 | 원금을 넘는 할인을 자를지 거절할지 정해라 | 보류 | 금액 경계 규칙의 두 번째 반례에서 나온 결정입니다. 근거가 없어 질문 후보로만 둡니다 |

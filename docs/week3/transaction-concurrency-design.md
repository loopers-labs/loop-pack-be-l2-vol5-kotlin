## 1. 브랜드 일괄 삭제 — `DELETE /api-admin/v1/brands/{brandId}`

| 함께 성공하거나 함께 실패해야 하는 것 | 건드리면 안 되는 것 |
| --- | --- |
| 브랜드 삭제, 그리고 그 브랜드에 연결된 (아직 안 지워진) 상품 전체의 삭제. 재고가 0인 상품도 포함합니다 | 다른 브랜드와 그 상품들, 기존 주문의 품목, 수량, 단가, 총액, 포인트 결제 결과 |

#### DS-14 · 트랜잭션을 어디서 시작할까

- 시나리오
  - 브랜드를 삭제할 때 해당 브랜드에 연결된 상품들도 삭제처리가 되어야 한다
- 구현 방법
  - 1 - `BrandFacade.delete`에 `@Transactional` 을 붙인다
  - 2 - Brand 존재 검증(없으면 예외: 404)
  - 3 - `brandId`에 연결된 상품을 삭제한다
  - 4 - Brand를 삭제 처리 한다
- 이유와 비용:
  - 브랜드와 상품은 서로 다른 service 라서, 각 service 의 `@Transactional` 만으로는 둘이 따로 커밋된다. 둘을 하나로 묶으려면 둘을 함께 부르는 Facade 에서 트랜잭션을 시작해야 한다.
  - 확인: Facade 의 `@Transactional` 을 일부러 떼면 "브랜드 삭제가 실패했는데 상품 삭제는 커밋된 채로 남는" 롤백 테스트가 실패한다.
  - 4번에서 브랜드를 **다시 읽어서** 지운다. 3번의 벌크 UPDATE 가 영속성 컨텍스트를 비우기 때문에, 그 전에 읽어 둔 Brand 는 분리된 상태이고 거기에 `delete()` 를 해도 DB 에 저장되지 않는다. 처음 읽은 Brand 에 `delete()` 하도록 바꿔 봤더니 브랜드 삭제가 DB 에 남지 않았다.
  - 비용: 트랜잭션 경계를 application 계층(Facade)이 갖는다. 주문 확정도 같은 방식이다.

#### DS-15 · 연결 상품을 어떻게 지울까

- 구현 방법
  - JPQL UPDATE 한 문장으로 한 번에 지운다
    - `@Query("update Product p set p.deletedAt = :now, p.updatedAt = :now where p.brandId = :brandId and p.deletedAt is null")`
    - `@Modifying(flushAutomatically = true, clearAutomatically = true)`를 함께 사용해서 영속성 컨텍스트에 존재하는 캐시를 지우고 진행한다
- 이유와 비용:
  - 하나씩 지우면 상품 수만큼 SELECT 와 UPDATE 가 나가고, 중간에 실패할 지점도 그만큼 늘어난다. 한 문장이면 DB 가 그 문장 전체를 원자적으로 처리한다.
  - `deleted_at is null` 조건 덕분에 이미 지워진 상품의 삭제 시각은 덮어쓰지 않고, 재고가 0인 상품도 포함된다.
  - 비용 1: 벌크 UPDATE 는 엔티티 콜백(`@PreUpdate`)을 거치지 않아서 `updatedAt` 을 직접 넣어야 한다.
  - 비용 2: 영속성 컨텍스트와 DB 가 어긋난다. 그래서 `clearAutomatically` 를 켰고, 이게 위 DS-14 의 "다시 읽기" 순서 제약을 만든다.
  - 실험: `flushAutomatically`, `clearAutomatically` 를 둘 다 빼도 지금 흐름에서는 테스트가 전부 통과한다. 이 트랜잭션 안에서 상품을 읽거나 고치지 않기 때문이다. 옵션을 유지할지(나중에 같은 트랜잭션에서 상품을 읽게 될 때의 보험) 뺄지(순서 제약 제거) 는 아직 정하지 않았다. **직접 정하기**

## 2. 최초 주문 확정 — `POST /api/v1/orders/{orderId}/confirm`

| 함께 성공하거나 함께 실패해야 하는 것 | 건드리면 안 되는 것 |
| --- | --- |
| 재고 차감, 포인트 차감, 주문 상태를 `CONFIRMED` 로 변경, 결제 결과 저장 | 실패한 주문은 `DRAFT` 그대로, 재고와 잔액도 확정 전 그대로 |

- 주문 확정
  - 주문 생성 다음 실제 결제가 일어나는 API
  - 재고와 포인트 사용, 상태 `CONFIRMED` 변경, 결제 금액 저장.
- 이미 확정된 주문을 다시 확정하면 지금처럼 ORDER_NOT_DRAFT로 거절합니다. 중복 요청을 알아보는 키나, 처음 성공 응답을 다시 돌려주는 기능은 이번에 만들지 않는다.(과제 요구사항)

### 호출 경로

| 순서 | 어디서 | 무슨 일 | DB |
| --- | --- | --- | --- |
| 1 | `OrderV1Controller.confirm` | `OrderFacade.confirm` 호출 | |
| 2 | `OrderFacade.confirm` (`@Transactional`) | 프록시를 거쳐 들어오면서 트랜잭션 시작 | |
| 3 | `UserService.getActiveOrThrow` | 요청자 확인 | SELECT |
| 4 | `OrderService.getDraftOwnedForUpdateOrThrow` | 본인 주문인지, DRAFT 인지 확인. 만료 여부는 Facade 에서 확인 | SELECT … FOR UPDATE (주문 행 잠금) |
| 5 | `OrderService.getItems` | 품목 조회 | SELECT |
| 6 | `ProductService.getAliveAllForUpdateOrThrow` | 상품이 살아 있는지 확인하며 잠금. id 오름차순 | SELECT … FOR UPDATE (상품 행들 잠금) |
| 7 | `OrderFacade` 안 | 판매 가능 여부 확인, `decreaseStock` (메모리에서만 변경) | |
| 8 | `PointService.use` | 포인트 행 잠금, 잔액 확인과 차감, 원장 INSERT | SELECT … FOR UPDATE, INSERT |
| 9 | `Order.confirm` | 상태와 결제액 변경 (메모리) | |
| 10 | 커밋 | 변경 감지로 상품, 포인트, 주문 UPDATE 후 락 해제 | UPDATE |

- 프록시: 모든 호출이 서로 다른 bean 사이의 호출이라 같은 클래스 안 호출(자기 호출)이 없다. 안쪽 service 의 `@Transactional` 은 2번 트랜잭션에 참여한다.
- `REQUIRES_NEW` 로 따로 커밋되는 곳이 없고, 예외를 잡고 넘어가는 `catch` 도 없다. 그래서 어느 단계에서 예외가 나도 그대로 밖으로 나가고 전부 롤백된다.
- 잠금 읽기(`FOR UPDATE`)를 하는 service 메서드는 읽기 전용이 아닌 `@Transactional` 로 바꿨다.
- 확인: Facade 의 `@Transactional` 을 떼면 롤백 문제가 아니라 **조용히 저장되지 않는다**. 예전에는 연관관계 때문에 `LazyInitializationException` 으로 먼저 깨졌지만, 연관관계를 없앤 뒤로는 재고와 주문 상태가 저장되지 않는다 (테스트로 확인). 포인트와 원장은 `PointService` 가 자기 트랜잭션으로 따로 저장될 것이라 서로 어긋날 수 있다고 추정하지만, 직접 확인하지는 않았다.

#### DS-16 · 데이터를 어떤 순서로 잠글까

- 고른 것: 주문 → 상품(id 작은 것부터) → 포인트 순서로 잠근다. `confirm`, `cancel`, 충전, 관리자 상품 수정이 모두 이 순서를 지킨다. (한 요청이 여러 종류를 같이 잠그는 건 `confirm` 뿐이다.)
- 이유와 비용:
  - 주문을 제일 먼저 잠그는 이유: 주문은 주문마다 행이 따로라서 서로 기다릴 일이 없고, 여기서 "내 주문인지, 아직 DRAFT 인지, 만료됐는지"를 먼저 확인할 수 있다. 상품을 먼저 잠그면 어차피 거절될 요청도 재고 행 앞에서 줄을 서게 되고, 그 사이 정상적인 구매자까지 같이 기다린다. 요청이 몰리는 행은 가장 늦게 잠그고 가장 짧게 쥐는 게 낫다.
  - 상품을 id 작은 것부터 잠그는 이유: 두 주문이 같은 상품을 반대 순서로 담았다고 해 보자([a,b]와 [b,a]). 한쪽은 a를 쥔 채 b를 기다리고, 다른 쪽은 b를 쥔 채 a를 기다리다가 둘 다 멈춘다(교착). 둘 다 id 작은 것부터 잠그면 이런 일이 없다. 어느 경로든 같은 순서로 잠가야 한다.
  - 상품 다음에 포인트를 잠근 건 `confirm` 이 원래 이 순서로 읽고 있어서, 코드를 억지로 뒤집지 않으려고 했다.
  - 한계: 포인트를 상품보다 나중에 잠가서, 한 사용자의 포인트 경쟁 때문에 기다리는 동안에도 공용 상품 행을 쥐고 있게 된다.

## 3. 같은 재고·잔액을 동시에 바꿀 때

### 같은 데이터를 바꾸는 기능

#### DS-17 · 상품(재고)을 어떻게 보호할까

- 시나리오
  - 구매자 여러 명이 구매를 하려는데, 관리자가 상품 데이터를 수정하는 경우
- 생각 정리
  - 구매자가 여러 명이 구매를 한다: 재고 차감
  - 관리자가 상품 판매 중단을 했으나 구매를 한다: 상품 판매 상태 변경 --> 이 경우와 상품 재고와는 다른 얘기 인 것 같음.
  - 상품의 경우 일단 구매 되었다가 나중에 자동 취소 되어도 괜찮다고 생각함. 그렇다면 '일단 받고 나중에 취소' -> 강한 락을 걸 필요가 없지 않나?
    - 취소 경로를 잘 확인 할 것
    - 확인: 지금 코드에는 확정 뒤의 취소(환불) 경로가 없다. `Order.cancel` 은 DRAFT 만 취소하고 "차감한 것이 없어 되돌릴 처리가 없다". 그래서 '일단 받고 나중에 취소'는 이번에 쓸 수 없다. 취소와 재고 복구 경로를 먼저 만들어야 가능한 선택지다.
  - 궁금) 상시 판매하는 상품 종류와 선착순 N개 판매와 같은 인기 많은 상품을 나눠서 락 종류를 선택하게 만들 수도 있을까?
    - 가능은 하다. 그런데 엔티티는 동일한데 시나리오마다 다르게 실제로 관리하게 되는지... 궁금 
- 고른 것: **비관적 잠금** (`SELECT … FOR UPDATE`). 확정과 관리자의 이름·가격·재고·상태 수정과 삭제가 같은 규칙을 따른다
- 이유와 비용:
  - 한 상품 행에 여러 구매자가 몰리는 경쟁이기 때문.
  - 관리자 수정도 잠그는 이유: JPA 는 행 전체를 UPDATE 한다. 이름만 고치는 요청도 읽어 둔 재고 값을 되돌려 쓸 수 있다. 확정과 겹친 이름·가격 수정에서 잠금을 빼면 확정된 재고 차감이 사라지는 것을 테스트로 확인했다.
  - 비용: 줄을 서는 동안 DB 연결을 쥐고 있고, 대기 시간 설정에 따라 오래 기다린다. 대기 시간 때문에 그만큼 커넥션 pool을 사용하고 있다.
    - 궁금) 현재 3초라는 타임아웃을 설정했으나, 실제로는 타임 아웃에 대한 기준을 어떻게 잡으면 좋을지? 시나리오마다 다를 수는 있을 것 같은데...

#### DS-18 · 포인트(잔액)를 어떻게 보호할까

- 시나리오
  - 구매자 한 명이 동시에 포인트와 관련된 요청을 여러개 보내는 경우
- 고른 것: **비관적 잠금**. 포인트 사용과 충전이 같은 행을 잠그고 시작한다
- 이유와 비용:
  - 같은 사용자의 서로 다른 주문 세 개가 동시에 확정되는 경우(잔액 10,000원에 4,000원짜리 3건)와, 충전과 결제가 겹치는 경우가 같은 포인트 행을 읽고 바꾼다. 잠금이 없으면 3건이 모두 확정되거나, 충전한 2,000원이 사라져 잔액이 3,000원이 된다.
  - 상품별 잠금만으로는 같은 사용자의 서로 다른 상품 주문 간 경쟁을 막지 못한다. 상품이 서로 달라도 포인트 행은 하나이기 때문이다.
  - 비용: 잔액 조회는 잠그지 않아서 읽는 쪽은 기다리지 않지만, 쓰는 쪽은 사용자별로 줄을 선다.
  - 한계: 포인트 행이 아직 없는 처음 충전은 잠글 행이 없다 (5절).
- 같은 구매 정보를 여러 번 보내거나 외부 결제 재시도에 대한 생각은 이번 과제가 금지한 범위(새 요청키 체계, 성공 응답 재사용)와 겹쳐서 5절로 옮겼다.

#### DS-19 · 주문 상태를 어떻게 보호할까

- 시나리오
  - 같은 주문의 요청이 여러번 들어오는 경우
  - 같은 주문에 대해서 서로 다른 status로 요청 오는 경우
- 생각 정리
  - 확정과 취소가 동시에 올 때 요청 순서대로 처리되어야 한다.
    - 확정 -> 취소: 1회 결제 완료 후 취소(환불)
    - 취소 -> 확정: 상품 주문 오류(취소) -> 주문 완료 순으로 동작 되어야함. 사용자가 직접 상품 재 취소가 가능하기 때문이다.
- 고른 것: **비관적 잠금**. 확정과 취소가 주문 행을 `FOR UPDATE` 로 잠그고 DRAFT 인지 본다
- 이유와 비용:
  - 락이 왜 필요한가: 같은 주문을 두 요청이 동시에 확정하면, 둘 다 "아직 DRAFT" 라고 읽고 통과한다. 그 뒤의 재고와 포인트는 각자 정당하게 쓰는 것처럼 보여서 포인트 락이나 상품 락으로는 두 번째가 막히지 않아 이중 차감 문제가 일어난다.
  - 같은 사용자가 A(상품 a,b) 주문과 B(상품 b,c) 주문을 동시에 확정하는 경우: 포인트는 한 행이라 포인트 락이 잔액을 지키고, 상품 b 는 두 주문이 겹치니 상품 락이 필요하다. 각각 서로 다른 것을 지킨다.
  - 확정과 취소가 동시에 오면 먼저 주문 행을 잡은 쪽이 끝난 뒤 다른 쪽이 최신 상태를 읽는다. 확정이 먼저면 취소는 `ORDER_NOT_DRAFT`, 취소가 먼저면 확정이 `ORDER_NOT_DRAFT` 다. 지금 코드에서 확정 뒤 취소(환불)는 없으므로 "확정 → 취소" 는 취소가 거절되는 것으로 끝난다.
  - 비용: 주문 락은 같은 주문 요청끼리만 서로 기다려서 다른 주문에는 영향이 없다.

요청 결과와 DB 에 남은 주문, 품목, 잔액을 함께 보고 확인합니다.

- 재고: 처음 재고 − 성공한 주문의 수량 합 = 최종 재고
- 잔액: 처음 잔액 + 성공한 충전 합 − 성공한 결제 합 = 최종 잔액
- 개수: 성공 + 업무 거절 + 기술 오류 = 전체 요청 수

"최종 재고가 음수가 아니다"만 확인하고 끝내면 안 됩니다. 요청을 전부 거절해도 그 조건은 통과하기 때문입니다.

#### DS-20 · 테스트에서 중간 실패를 어떻게 만들까

- 고른 것
  - 브랜드 삭제: `@SpykBean` 으로 `BrandService.delete` 를 실패시킨다. 그 앞의 상품 일괄 UPDATE 는 실제로 실행된다.
  - 주문 확정: `@SpykBean` 으로 `PointTransactionRepository.save` 를 실제 호출한 뒤 `flush()` 하고 예외를 던진다. 재고 UPDATE, 포인트 UPDATE, 원장 INSERT 가 DB 로 나간 뒤에 실패한다.
- 이유와 비용:
  - 변경 SQL 이 나가기 전에 예외를 던지면 메모리의 변경이 버려질 뿐이라 롤백을 검증한 게 아니다. 기존 롤백 테스트는 이 경우였다 (SQL 로그로 확인).
  - 주문 확정은 실패 시점에 **다른 연결로 커밋되지 않은 값을 읽어서** (READ UNCOMMITTED) 재고, 잔액, 원장이 이미 DB 에 나가 있었음을 확인하고, 트랜잭션이 끝난 뒤 새로 읽어 처음 상태인지 확인한다. flush 된 값과 commit 된 값을 구분한 방법이다.
  - 비용: 브랜드 쪽은 "저장 경계" 가 아니라 service 메서드에서 실패시킨다. 과제는 저장 경계에서 유발하라고 하니, repository 쪽으로 옮길지는 따로 판단한다.
  - 주의: `@SpykBean` 은 `@Nested` 와 함께 쓰면 설정이 다음 테스트로 샌다. `@AfterEach` 에서 원래 동작으로 직접 되돌렸다.

### 동시 요청 테스트를 짤 때 지킬 것 (과제)

- 테스트 데이터는 요청을 보내기 **전에** 저장하고 커밋합니다. 테스트 전체를 하나의 트랜잭션으로 감싸지 않습니다.
- 요청마다 따로 트랜잭션을 쓰고, 진짜 스프링 bean 을 부릅니다. 실제 MySQL(Testcontainers)을 씁니다. 메모리 DB 나 저장소 mock 으로는 잠금과 롤백을 확인할 수 없습니다.
- 요청을 동시에 출발시키는 신호와, 끝나기를 기다리는 곳에 시간 제한을 둡니다. 시간 초과를 업무 거절로 세지 않습니다.
- 요청마다 결과(성공, 업무 거절, 기술 오류)를 모읍니다. 예외를 출력만 하고 버리지 않습니다.
- 모든 요청이 끝난 뒤 DB 를 새로 읽어서 확인합니다. `finally` 에서 기다리던 것을 풀고 스레드 풀을 정리합니다.
- `Thread.sleep` 이나 반복 횟수를 늘려서 우연히 실패하기를 기다리지 않습니다.
- "두 트랜잭션이 다 읽을 때까지 기다렸다가 쓰기"는 대조군에서만 씁니다. 실제 서비스 테스트는 출발만 맞춥니다.
- 테스트 이름 예: `BrandRemovalTransactionTest`, `OrderTransactionTest`, `OrderConcurrencyTest`

> 알아 둘 것
> - 테스트 환경의 DB 연결은 최대 10개이고, 연결을 3초 안에 못 받으면 실패합니다 (`jpa.yml`). 8건은 괜찮지만 12건으로 늘리면 연결이 모자라서 기술 오류가 섞일 수 있습니다.
> - MySQL 은 잠금을 기본 50초까지 기다리지만, 이 프로젝트는 `jpa.yml` 의 `connection-init-sql` 로 3초로 줄였습니다 (`LockTimeoutTest`). 테스트의 시간 제한은 이보다 길어야 합니다.
> - 2주차 테스트는 테스트 메서드에 트랜잭션이 없고, 확인할 때 저장소로 다시 읽습니다. "트랜잭션이 끝난 뒤 새로 읽기"를 그대로 쓸 수 있습니다.
> - 여러 테스트가 같이 쓸 실행 코드(헬퍼)는 처음부터 만들지 않아도 됩니다. 두 번째 테스트에서 같은 코드가 반복될 때 뽑으면 됩니다. (동시 실행기 `ConcurrentRunner` 는 경쟁 테스트가 둘 이상이 되면서 뽑았다.)

## 5. 하지 않은 것, 확인하지 않은 것

- **외부 결제** — 결제는 전부 포인트입니다 (기획 3-2절, P-18, P-26). 트랜잭션은 DB 변경만 되돌립니다. 카드나 PG 같은 외부 호출이 생기면, 이미 보낸 결제 요청은 롤백으로 취소되지 않습니다. 결제 수단이 여러 개가 되면 `payment`, `payment_line` 같은 구조가 필요합니다 (설계 DS-12).
- **새 요청키 체계, 성공 응답 재사용** — 이번 과제가 만들지 말라고 한 범위입니다. DS-18 에 적었던 생각을 옮겨 둔다.
  - 구매 정보의 UK 값(`orderId`)으로 항상 같은 결과를 내고, 클라이언트가 차감 전후 포인트 내역을 함께 보내 검증하자는 안: 클라이언트가 보낸 값을 믿는 구조라 만들지 않았다. 이미 확정된 주문은 기존 `ORDER_NOT_DRAFT` 로 거절한다.
  - 충전 재시도를 외부 결제의 `purchaseCode` UK 로 막자는 안: 지금은 외부 결제가 없어서 해당 없음. 외부 연동이 생기면 다시 본다.
- **처음 충전하는 사용자** — point 행이 아직 없습니다. 첫 충전 요청 두 개가 동시에 오면 어떻게 되는지 확인하지 않았습니다 (DS-18). 잠글 행이 없어서 비관적 잠금도 이 경우는 지켜 주지 못합니다.
- **브랜드 이름 수정과 브랜드 삭제가 동시에** — 브랜드도 행 전체를 다시 쓰기 때문에 삭제가 되돌려질 수 있습니다. 확인하지 않았습니다.
- **브랜드 삭제와 주문 확정이 동시에** — 확정은 상품 행을 `FOR UPDATE` 로 잡으니 벌크 UPDATE 가 그 락을 기다릴 것으로 추정할 뿐, 동시 실행 테스트는 만들지 않았습니다.
- **`PRODUCT_REMOVED`** — 삭제된 상품을 고객에게 "더 이상 판매하지 않는다" 로 알리는 새 오류 코드. 구현하지 않았고 지금은 `*_NOT_FOUND` (404) 입니다.
- **고객 목록·상세, 내 좋아요 목록, 새 주문 생성** — 브랜드 삭제 뒤의 동작을 브랜드 삭제 경로로 확인한 테스트가 없습니다 (1절 표).
- **중간 실패의 주입 위치** — 브랜드 쪽은 저장 경계가 아니라 service 메서드에서 실패시켰습니다 (DS-20).
- **대표 HTTP 사례** — 브랜드 삭제 실패와 주문 확정을 이번 락과 함께 E2E 로 다시 확인하지 않았습니다.
- **ArchUnit** — 변경한 코드를 실제로 검사하는지 따로 확인하지 않았습니다.
- **`ORDER BY id` 의 필요성** — 교착을 막는다고 증명하지 못했습니다 (4절).
- **포인트 락을 상품 앞으로 당기기** — 개선 후보로만 남겼습니다 (DS-16).
- **조건부 갱신 (다음에 생각)** — 이번에는 비관적 잠금과 낙관적 잠금 두 가지 중에서만 고릅니다. `UPDATE … WHERE stock >= ?` 처럼 확인과 변경을 SQL 한 문장으로 하는 조건부 갱신은 고르지 않았습니다. 앞서 적어 둔 생각과 알게 된 점을 남겨 둡니다.
  - 직접 적은 이유 (DS-17): 현재 SQL이 어떤식으로 구동되는지 확인을 따로 해봐야겠지만, 비관적 잠금과 낙관적 잠금의 경우 상품 재고 차감에 대해 서비스가 맡아 DB로 전송하면서 락을 발생시키기 때문에 경합이 발생해 필연적으로 느려질 수밖에 없는 환경이지만, 조건부 갱신의 경우 개수 차감하는 주체가 DB가 되기 때문에 경합이 발생하지 않는다 (비교적 발생하지 않는다?) 물론 별도의 명시적 락 없이도 Race Condition을 방지할 수 있어 매우 효율적이지만, 현재 값을 읽어 복잡한 비즈니스 분기 처리를 해야 하는 경우에는 적용하기 어렵다. 단순 수량 증감(좋아요 수 증가, 선착순 쿠폰 발급, 재고 차감)에 추천하는 로직
  - 알게 된 점
    - `UPDATE` 도 실행하는 순간 그 행을 커밋할 때까지 잠급니다. 경합이 없는 게 아니라, 읽을 때가 아닌 바꿀 때부터 잠그는 것입니다.
    - 낙관적 잠금도 내부는 버전 조건부 UPDATE 입니다. 다만 조건이 "아무도 안 바꿨나"라서 재고가 충분해도 동시에 오면 한쪽이 실패합니다. 조건부 갱신은 "충분한가"를 조건으로 걸기 때문에 둘 다 성공합니다.
    - MySQL 의 `UPDATE` 는 바뀐 행 수만 돌려주고 바뀐 값은 돌려주지 않습니다. 그래서 포인트 내역에 "거래 후 잔액"을 적으려면 잔액을 다시 읽어야 합니다. 이미 불러온 객체는 옛날 값이라, 잔액 숫자만 따로 조회해야 합니다.
    - 잔액 부족, 잔액 상한 같은 규칙이 SQL 조건으로 옮겨 가면서 엔티티와 SQL 두 곳에 나뉩니다. 규칙을 `Point` 엔티티 한 곳에 두려면 비관적 잠금이 맞습니다.
    - 바뀐 행이 0일 때 "재고 부족"인지 "없거나 삭제됨"인지는 SQL 결과만으로 구분되지 않습니다.
    - 재고만 SQL 로 줄이면, 관리자 수정처럼 행 전체를 다시 쓰는 기능이 재고를 옛날 값으로 되돌리는 문제는 따로 막아야 합니다.
- **선택 과제** — 하면 결과를 적고, 안 하면 "안 함"으로 남깁니다.
  - [ ] 다른 잠금 방법과 비교 — 안 함 (비관적만 구현. 재고는 비관적, 포인트·주문은 낙관적으로 섞는 안은 설명만 했고 구현하지 않음)
  - [ ] 재고 요청을 12건으로 늘린 실험 — 안 함
  - [ ] 브랜드 삭제와 상품 등록을 동시에 실행 (지금 `ProductFacade.create` 는 브랜드 확인과 상품 등록이 서로 다른 트랜잭션입니다) — 안 함

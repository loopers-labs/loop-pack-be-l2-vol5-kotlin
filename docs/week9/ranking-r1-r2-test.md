# 주간 랭킹 r1 + r2 산정 테스트

2026-11-19, r1 합계 + r2 늦은 구매 합계로 랭킹을 매기는 지금 방식에서 점수가 틀어지는 경우를 테스트로 드러냈다. 테스트는 `WeeklySalesSnapshotJobE2ETest` 에 있고, 코드는 고치지 않았다.

- 주 W 는 2026-11-09 주 (`2026_11_2`) 다. W 의 r1 은 `launch("2026-11-16")`, W 의 r2 는 `launch("2026-11-23")` 의 스냅샷 스텝이 만든다.
- 구매가 언제 저장됐는지는 `createdAt` 을 직접 넣어 만든다. 시계 차이나 늦은 커밋도 이 값으로 흉내 낸다.
- 판정 기준은 상품별 `r1 + r2 = 그 주 구매 활동 합계`, 그리고 랭킹이 한 가지 입력으로만 매겨졌는지다.
- 라이터는 upsert 다.

## r1·r2 기준을 바꾼 뒤

같은 날 r1·r2 기준을 바꿨다. r1 은 전주 확정분 중 월요일 00:00 전에 저장된 행, r2 는 00:00 이후에 저장된 행이고, 01:30 한 번 실행에서 둘 다 만든다. 아래 "결과" 부터는 바꾸기 전 기록이다.

- T0, T3 은 저장 시각을 00:00 이후로 넣고 `launch("2026-11-16")` 한 번으로 r1·r2 를 만들게 바꿨다. 통과한다.
- T1a, T1b, T2a, T2b 는 고치지 않았고 여전히 실패한다. 실패 이유는 달라졌다.

| 테스트 | 지금 결과 |
| ------ | --------- |
| T1a, T1b | 점수·순위 검사는 통과한다. r2 를 랭킹 전에 같은 스텝에서 만들어서 재시작 사이에 입력이 바뀌지 않는다. 테스트 안의 `launch("2026-11-23")` 이 다음 주 포인터(`2026_11_3`)를 하나 더 만들어, 포인터가 하나뿐이라고 본 검사에서 실패한다. |
| T2a | `createdAt` 을 지금 + 1 시간(00:00 이후)으로 넣어서 새 기준으로는 r2 다. r1 이 {1:3} 이어야 한다는 기대와 어긋난다. |
| T2b | 실행 뒤에 저장된 구매가 r2 에 들어가야 한다고 기대한다. 새 기준에서는 01:30 실행 뒤 저장분은 반영하지 않는다. |

## T0. 기본 회귀

상품 1 을 3 개, 상품 2 를 5 개 사고 r1 을 만든 뒤, r1 을 만든 뒤 저장된 구매로 상품 1 을 2 개, 상품 3 을 4 개 사고 r2 를 만든다. r1 + r2 가 그 주 구매 활동 합계와 같다. 지금 코드에서 통과한다.

## T1. 재시작 사이에 r2 가 생기는 경우

상품 1~150 을 수량 (200 − 상품 id) × 10 으로 산다. 동점이 없고 순위가 상품 id 와 같다. 상품 120 에서 랭킹 INSERT 가 실패하게 해서, 청크 100 이라 상품 1~100 은 커밋되고 두 번째 청크에서 잡이 `FAILED` 로 끝난다 (랭킹 100 행, 포인터 `FAILED`). 그다음 늦은 구매를 넣고 W r2 를 만든 뒤 W 를 같은 JobInstance 로 재시작한다.

기대값은 과제의 "완성된 입력은 재시작할 때 다시 복사하거나 추가하지 않는다" 를 따라 첫 실행과 같은 입력(r1)으로 매긴 결과다.

### T1a. 늦은 구매가 앞·뒤 절반에 하나씩

늦은 구매로 상품 50 에 +5000, 상품 130 에 +3 을 넣었다.

| 값       | 기대 (r1 만)     | 지금 코드       |
| -------- | ---------------- | --------------- |
| 잡       | `COMPLETED`, 같은 JobInstance | `COMPLETED`, 같은 JobInstance |
| 상품 50  | 1500 점, 50 위   | 1500 점, 50 위 (첫 실행에서 씀) |
| 상품 130 | 700 점, 130 위   | 703 점 (r1 + r2) |
| 포인터   | `PUBLISHED`, 150 | `PUBLISHED`, 150 |

앞 절반은 r1 만, 뒤 절반은 r1 + r2 로 매긴 랭킹이 섞인 채 공개된다. 상품 수가 같아서 공개 스텝이 걸러내지 못한다.

### T1b. 늦은 구매로 첫 청크 경계가 밀릴 때

늦은 구매로 상품 150 에 +5000 을 넣었다. 재시작 때 리더 정렬이 150, 1, 2, …, 149 로 바뀌고, 이미 읽은 100 개를 건너뛰면 상품 100 부터 다시 쓴다. 상품 150 은 한 번도 쓰이지 않는다.

- upsert 라서 상품 100 은 덮어쓰고 랭킹이 149 행이 된다.
- 공개 스텝이 `스냅샷 상품 수 = 150, 랭킹 상품 수 = 149` 로 `FAILED` 를 낸다. 다시 재시작해도 공개 스텝만 돌아 계속 실패한다.
- 기대값은 `COMPLETED`, 랭킹 150 행, 상품별 점수와 순위가 r1 만으로 한 번에 돌린 결과와 같은 것이다.

## T2. r1·r2 경계

r2 기준은 r1 스냅샷의 `MAX(created_at)`, 즉 배치 앱 시계다. 구매 활동의 `created_at` 은 스트리머 앱 시계다. 두 값을 비교하는 한, "r1 에 들어갔나" 와 "기준보다 뒤인가" 가 어긋날 수 있다.

### T2a. 두 번 세짐 (스트리머 시계가 앞섰을 때)

r1 을 만들기 전에 상품 1 을 3 개 사되 `createdAt` 을 지금 + 1 시간으로 넣었다. r1 에 들어갔는데 기준 시각보다 늦어서 r2 에도 들어간다.

| 값      | 기대         | 지금 코드 |
| ------- | ------------ | --------- |
| r1      | {1:3}        | {1:3}     |
| r2      | 없음         | {1:3}     |
| r1 + r2 | 3 = 구매 합계 | 6         |

### T2b. 빠짐 (스트리머 시계가 늦거나 커밋이 늦었을 때)

r1 을 만든 뒤에 상품 2 를 4 개 사되 `createdAt` 을 r1 스냅샷 `created_at` − 1 초로 넣었다. r1 을 만드는 동안 아직 커밋되지 않았던 구매와 같은 모양이다. r1 에 없는데 기준 시각보다 이르다고 r2 에서도 빠진다.

| 값      | 기대        | 지금 코드 |
| ------- | ----------- | --------- |
| r1      | {1:3}       | {1:3}     |
| r2      | {2:4}       | 없음      |
| r1 + r2 | {1:3, 2:4}  | {1:3}     |

## T3. r2 뒤에 도착한 구매

리비전을 r2 까지만 두기로 해서, r2 를 만든 뒤에 도착한 W 구매는 반영되지 않는다. 이 한계를 고정하는 테스트다. 정책이 바뀌면 기대값을 바꿔야 한다.

상품 1 을 3 개 사고 r1, r1 뒤 2 개를 사고 r2, r2 뒤 4 개를 사고 `launch("2026-11-30")` 을 돌렸다. W r1 {1:3}, W r2 {1:2}, W r3 없음, W r1 + r2 는 5 로 구매 합계 9 보다 4 적다. 늦게 온 4 개는 11 월 3 주 r2 에도 들어가지 않는다. 지금 코드에서 통과한다.

## 실패 주입

상품 120 에서 랭킹 INSERT 가 실패하게 하려고 `product_ranking` 에 CHECK 제약 (`product_id <> 120`) 을 걸었다가 재시작 전에 지웠다. 처음 계획한 `BEFORE INSERT` 트리거는 테스트 MySQL 의 binlog 가 켜져 있어 SUPER 권한이 필요해 만들 수 없었다 (에러 1419).

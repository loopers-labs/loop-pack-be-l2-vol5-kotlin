# 브로커를 죽여 보고 남긴 것

아웃박스가 브로커 장애를 받아내는지를 실제로 흔들어 확인한 기록이다.
숫자는 모두 로컬 1회 실행(2026-11-05)의 관찰값이며 성능 비교가 아니다.

## 구성

| 항목 | 값 |
|---|---|
| 브로커 | `kafka-1/2/3` · 토픽 `order.events.v1` · 파티션 3 · RF 3 |
| 프로듀서 | `commerce-api` · 결제 성공과 같은 TX 에서 아웃박스 적재, 커밋 뒤 직접 전송 · ack 오면 SENT |
| 릴레이 | `commerce-relay` · PENDING 을 id 순 500건씩 · ack 오면 SENT · 실험에서는 10초 주기 |
| 컨슈머 | `commerce-streamer` · `purchase-activity` · eventId 로 중복을 거른다 |
| 부하 | k6 `docs/week6/k6-order-events.js` · 주문 생성 → 확정(POINT) · 100 VU |
| api DB 풀 | 40 |

## 정상: 100 VU · 10초

| 항목 | 값 |
|---|---|
| 확정 성공 | 3,223 (277/s) |
| 아웃박스 | 3,223 행 · 전부 SENT · eventId 중복 0 |
| 토픽 증가 | +3,223 |
| 처리 기록 · 구매 활동 | 3,223 · 3,223 |

직접 전송만으로 끝났다. 릴레이가 할 일이 없었다.

## 브로커 셋 다 죽이기: 100 VU · 30초

시작 5초 뒤 `docker stop kafka-1 kafka-2 kafka-3`. 프로듀서 전달 제한(`delivery.timeout.ms` 기본
120초)을 넘기도록 약 2분 40초 뒤에 다시 띄우고 릴레이를 돌렸다.

| 시점 | 관찰 |
|---|---|
| 부하 중 | 확정 17,862 전부 성공 · p95 171ms. 브로커가 없어도 확정은 멈추지 않았다 |
| 죽기 전 | 1,747 건은 직접 전송으로 SENT |
| 죽은 뒤 | 16,115 건은 `Failed to send` 로그를 남기고 PENDING 으로 남았다 |
| 브로커 복구 후 릴레이 1회 | `relayed=16115` · 실패 0 |
| 최종 | 아웃박스 17,862 전부 SENT · eventId 중복 0 · 처리 기록 17,862 · 구매 활동 17,862 |
| 토픽 증가 | **+17,864** · 확정보다 2건 많다 |

### 토픽이 2건 많은 이유

주문 20226, 20288 은 브로커가 내려가는 순간에 보낸 메시지다. 브로커에는 기록됐는데 api 는
ack 를 받지 못해 실패로 남겼다. 그래서 행이 PENDING 으로 남았고 릴레이가 한 번 더 보냈다.
컨슈머가 eventId 로 걸러 구매 활동은 늘지 않았다.

아웃박스가 같은 이벤트를 두 번 내보내는 경로가 일부러 끊지 않아도 실제 장애에서 생긴다.
그 중복을 막는 것은 아웃박스가 아니라 컨슈머의 중복 거르기다.

### 컨슈머가 건너뛴 5건

| eventId | 왜 다시 왔나 |
|---|---|
| 20226 · 20288 | 위의 재발행 |
| 18859 · 18877 · 18922 | 브로커가 내려갈 때 반영은 했지만 오프셋 커밋을 못 해 다시 받았다 |

충돌과 DLT 는 0 이다.

## 확인한 것

- 확정된 주문은 브로커 상태와 상관없이 전부 아웃박스에 남는다.
- 브로커가 받은 것만 SENT 다. 못 받은 것은 PENDING 으로 남아 릴레이가 보낸다.
- 재발행이 생겨도 구매 효과는 주문당 한 번이다.

## 확인하지 않은 것

- 확정 거절(정상 3건 · 장애 27건, 모두 4xx)의 원인. 아웃박스와 무관해 보이나 보지 않았다.
- 브로커가 120초 안에 돌아오는 경우. 이때는 프로듀서 버퍼의 메시지가 늦게라도 나가 직접 전송이 SENT 를 찍을 것으로 예상하지만 재지 않았다.
- api 프로세스가 ack 직후 SENT 를 쓰기 전에 죽는 경우. 같은 재발행 경로로 예상한다.

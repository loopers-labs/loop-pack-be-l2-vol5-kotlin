# 늦은 구매 스냅샷 로컬 실행 결과

이 기록은 r2 를 "r1 고정 시각 뒤에 저장된 구매" 로 보고 그다음 주 실행에서 만들던 때의 결과다. 지금 기준(월요일 00:00 전후로 r1·r2 를 나누고 같은 실행에서 만든다)은 `ranking-batch.md` 에 있다.

2026-11-18 01:49 (KST), 로컬 `docker-mysql-1` 에서 `weeklySalesSnapshotJob` 을 두 번 돌려 11 월 2 주의 r1 과 r2 를 만들었다.

## 데이터

구매 활동을 새로 만들었다. 주문 테이블과는 연결하지 않았다 (`order_id` 는 10,000,001 부터).

| 항목      | 값                                                   |
| --------- | ---------------------------------------------------- |
| 구매 활동 | 1,539,838 행, 주문 1,100,000 개, 사용자 100,000 명   |
| 기간      | 2026-10-12 00:00 ~ 11-16 00:00 (UTC), 꽉 찬 5 주     |
| 분포      | KST 기준 저녁·주말에 많고 새벽에 적다. 상품 인기는 Zipf (s=0.85) |
| 정상      | 주문의 99%. `created_at` 이 `confirmed_at` 과 같다   |
| 늦은 구매 | 주문의 1%. 다음 주 월요일 01:30 (UTC) 부터 72 시간 안에 저장된다 |

- 11 월 2 주의 늦은 구매는 2,184 주문, 3,024 행이다.
- 저장 시각이 실행 시각보다 뒤인 행은 실행 직전 시각으로 당겼다.

## 실제 일정에 맞추기

2 주차 r1 은 원래 11-16 01:30 (UTC) 에 만들어진다. 그 시각에 맞추려고 이렇게 돌렸다.

1. 스냅샷·랭킹·포인터와 이 잡의 배치 기록을 비웠다.
2. 11-16 01:30 보다 늦게 저장된 행은 그때 없던 행이라, 1 차 실행 동안만 `deleted_at` 으로 가렸다.
3. 1 차 실행 뒤 r1 행의 `created_at` 을 11-16 01:30 으로 고치고, 가렸던 행을 되돌렸다.

## 1 차 실행 (11-16)

```bash
./gradlew :apps:commerce-batch:bootRun --args='--job.name=weeklySalesSnapshotJob requestDate=2026-11-16,java.time.LocalDate,false snapshotId=2026_11_2_r1'
```

잡은 `COMPLETED`.

- 2 주차 r1 `2026_11_2_r1` 을 만들었다. 상품 149,377 개, 수량 438,822.
- 1 주차 r2 `2026_11_1_r2` 도 만들었다. 1 주차 r1 이 없어서 1 주차 구매가 전부 들어갔다. 상품 149,994 개, 수량 444,138.
- 랭킹은 r1 으로 149,377 행을 썼고, 포인터 `2026_11_2` 는 `PUBLISHED`, 상품 수 149,377 이다.

## 2 차 실행 (11-23)

```bash
./gradlew :apps:commerce-batch:bootRun --args='--job.name=weeklySalesSnapshotJob requestDate=2026-11-23,java.time.LocalDate,false snapshotId=2026_11_3_r1'
```

잡은 `COMPLETED`.

- 2 주차 r2 `2026_11_2_r2` 를 만들었다. 상품 2,552 개, 수량 4,305.
- r2 는 11-16 01:30 뒤에 저장된 2 주차 구매 2,184 주문, 3,024 행과 정확히 같다.
- r1 438,822 + r2 4,305 = 443,127 로 2 주차 전체 판매 수량과 같다. 빠지거나 두 번 세진 구매가 없다.
- 3 주차 r1 은 구매가 없어 빈 채로 끝났고, 포인터 `2026_11_3` 은 `PUBLISHED`, 상품 수 0 이다.
- 랭킹은 r1 만 쓴다. 2 주차 랭킹은 r2 가 생겨도 그대로다.

| snapshot_id    | 상품 수 | 판매 수량 | 만든 시각 (UTC)             |
| -------------- | ------- | --------- | --------------------------- |
| `2026_11_1_r2` | 149,994 | 444,138   | 11-17 16:49 (1 차 실행)     |
| `2026_11_2_r1` | 149,377 | 438,822   | 11-16 01:30 (일정 시각으로 고침) |
| `2026_11_2_r2` | 2,552   | 4,305     | 11-17 16:49 (2 차 실행)     |

## r1 + r2 로 랭킹 다시 매기기

2026-11-18 02:13 (KST), 리더가 r1 과 r2 를 상품별로 더하도록 바꾼 뒤 2 주차 랭킹을 다시 매겼다. 위 2 차 실행 때까지는 랭킹이 r1 만 썼다.

1. 2 주차 r2 와 11-23 실행 기록을 지우고 `requestDate=2026-11-23` 으로 다시 돌렸다. r2 는 늦은 구매만 담아 상품 2,552 개, 수량 4,305 로 다시 만들어졌다.
2. 2 주차 랭킹·포인터와 11-16 실행 기록을 지우고 `requestDate=2026-11-16` 으로 다시 돌렸다. 스냅샷 스텝은 이미 있는 스냅샷이라 건너뛰고, 랭킹 스텝이 r1 과 r2 를 함께 읽었다.

두 번 다 `COMPLETED`.

| 항목                 | 상품 수 | 판매 수량 |
| -------------------- | ------- | --------- |
| `2026_11_2_r1`       | 149,377 | 438,822   |
| `2026_11_2_r2`       | 2,552   | 4,305     |
| 2 주차 랭킹 (r1 + r2) | 150,603 | 443,127   |

- r1 과 r2 에 둘 다 있는 상품 1,326 개는 판매 수량이 더해졌다. 상품마다 랭킹 점수와 r1 + r2 합을 비교해 다른 행이 없었다.
- 순위는 1 부터 256 까지다.
- 포인터 `2026_11_2` 는 `PUBLISHED`, 상품 수 150,603 이다. 공개 스텝이 r1 과 r2 를 합친 상품 수와 랭킹 행 수를 비교했다.
